    1.2.1 软件架构的定义¶

    软件架构的定义可以浓缩为以下三个要素：

    • 组成架构的元素：构件/组件（components）
    • 构件的相互联系：连接
    • 构件之间的相互关系：连接关系

    2.3 架构是软件迭代开发的框架¶

    2.3.1 架构¶

    1.软件产品和产品线的基本概念

    产品线的一般定义：满足特定市场或用户需求的，有一组公共的、可管理的产品特性的，符合上述两个条件的产品的组合。

    3.软件产品线核心资源的转化

    1）核心资源的输入

    （1）产品约束：构成产品线的各个产品的相同和不同点、行为特征、市场和技术预测、采用的标准、遵守的限制、与外部的接口、质量要求等。

    （2）风格、模式和框架：质量特性的适宜策略（对安全性、高性能与代价的妥协策略）、设计模式。架构描述了子系统之间的相互作用、模式是更小模块之间的相互作用。

    （3）生产约束：产品使用的行业、企业标准,基础平台描述,商用构件说明等。

    （4）生产策略：自顶向下还是自底向上？成本分解方法、自制外购策略等。

    （5）现有资源清单：在产品线工作开始的时候，可以利用的软件资源、库、算法、工具和构件的一览表等。

    2）核心资源的输出

    （1）产品线规范：构成产品线产品的描述，即它们的特征、操作、性能、属性、运行的平台等。

    （2）核心资源：核心资源是产品线中产品生产的基础,包括产品共享的框架、贯穿产品线进行系统化重用所开发的软件构件。

    （3）产品线架构：可以满足产品线通用性和各个产品特殊性的软件架构，指定了产品线中产品的结构、构件的接口规范。

    （4）与核心产品相对应的规则和附属过程：规则与附属过程指明核心资源是如何被应用到实际产品中。包括基线需求、允许的变化点、添加的需求、架构可支持的变化和扩展、支持实现的工具、技术和管理过程定义、计划等。

    （5）生产计划：指明如何将单个过程装配成产品。即生产者的产品开发指导手册

    ★软件架构对软件产品线开发的作用：¶

    1. 固化核心知识
    2. 提供可重用资产
    3. 缩短推出产品的周期
    4. 降低开发和维护的总成本
    5. 提高产品质量
    6. 支持批量定制

    开发：一个描述核心资源（或产品）如何实现的通用术语

    领域：一个专业技能和相关功能的集合。

    ★软件架构重构：¶

    软件架构重构是指对软件架构进行比较大的修改和调整，使它适应新需求，以及开发和维护的需要。

    软件架构重构属于“再工程”的一种情况，一般会经历逆向工程、重新规划、正向工程三个步骤。

    何时进行架构重构？

    • 架构太混乱，以致于进行一个小修改都会牵动全身
    • 将要进行的软件升级力度很大，原先的架构已不再适用新的需求了。

    2.4 架构是软件过程管理的基础¶

    2.5 需求、系统设计、软件过程和组织对架构的影响¶

    质量属性：一个系统或产品在满足其功能需求之外，所表现出的非功能性特征。

    常见的质量属性有：性能、可靠性、可用性、安全性、易用性、可移植性、可修改性、可测试性等

    2.5.1 需求影响架构¶

    影响架构的这些需求是：

    1. 项目的总体范围
    2. 不同功能开发的重要性和顺序优先权
    3. 与外部构件和系统的接口规范和标准
    4. 开发资源的分配
    5. 开发时间表的制定
    6. 软件各质量属性的选择和通过标准的制定
    7. 对软件各种质量的测试范围
    8. 软件发行通过关口的检测标准等

    2.5.4 组织影响架构¶

    在对软件架构的影响方面，组织更关心以下几个方面：

    1. 直接影响：如希望如何纳入到产品线中。
    2. 长远影响：如关注市场和行业的布局，并按产品线方向发展。
    3. 组织结构的影响：是自己开发，还是软件外包，自己的优势在哪里

    2.5.5 架构的反作用¶

    反之，架构也会产生反作用，包括：

    1. 架构影响开发组织的内部组织结构
    2. 架构影响开发组织的经营目标
    3. 架构可能会影响客户对下一个系统的需求
    4. 构建某个系统的实践过程丰富了整个开发团队的经验，从而将影响设计师对后继系统的设计
    5. 几个典型的系统会影响并实际改变软件工程的发展，以及开发人员学习和实践的技术环境等。

    2.6 架构师的作用、任务与责任¶

    2.6.1 架构师的作用¶

    在软件组织中，架构的作用如此之大，架构师的作用则非常明显。架构师应该起到的作用如下：

    1. 探索者

    ​ (1)为企业的商业利益不断探索新技术的运用;

    ​ (2)为提高竞争能力寻找和尝试优化的解决方案

    1. 设计师

    ​ 将优秀的功能和性能、关键质量特性带到软件中去。

    1. 倡导人

    ​ (1)为开发出真正能为用户提供最佳服务的软件而做用户利益的倡导人, 倾听和观察用户的回馈;

    ​ (2)推动开发团队建立前瞻性的战略眼光。

    Chapter 3 软件架构的描述与可视化¶

    3.1 架构描述与架构视图¶

    ★架构视图的定义：架构视图是对于从某一视角看到的系统所做的简化描述，它涵盖了系统的某一特定方面，而省略了与此方面无关的实体。

    3.1.1 五个基本架构¶

    为了满足整个软件生命周期中，了解、理解架构设计思想和实现目标的需要，可以首先从以下5个方面描述和认识架构。

    1. 开发架构：反映的是开发期的质量需求。表明开发过程应遵循软件系统开发期的特点，特别是有关产品线技术管理的要求，并制定/满足相应的设计决策；它的具体涉及对象是程序包、第三方构件、框架。

    2. 物理架构：反映安装和部署需求。它考虑软件系统与硬件环境的对应关系，设计部署和安装方案等；这里主要考虑主机、存储、网络的具体物理部署。

    3. 运行架构：反映的是运行期的质量需求。它针对系统运行要求，例如，与分布并发、实时等性能、安全有关的要求，制定/遵循相应的设计决策；它与进程、线程、对象,以及架构的关键运行机制有关。

    4. 逻辑架构：反映的是功能需求是如何被分解和协同实现的。逻辑架构设计是规划组成系统的所有模块，为它们分配不同的职责，使得这些构件能通过协作，完成功能需求；它的具体涉及对象是系统的逻辑层次、功能构件和类的划分、交互等。

    5. 数据架构：反映的是数据需求。在这里应考虑数据的分布、生成与应用的关系，设计合适的数据持久化存储和传递策略等。数据存储格式、数据字典、安全备份、复制、同步、数据传递是这里主要考虑的内容

    Chapter 4 从需求到架构¶

    4.1 架构师的需求过程¶

    需求工程的定义：

    需求工程是提供一种适当的机制，以了解用户想要什么、分析需求、评估可行性、协商合理的解决方案、确认规约以及在开发过程中管理这些被确认的需求规约的过程。

    （上图中需求定义过程也可以叫需求开发过程）

    需求跟踪矩阵（Requirement Trace Marix）：

    是为了杜绝需求遗漏的表格。主要是跟踪和统计功能需求和非功能需求。当需求基线第一次形成时就需要填写这个文档，这篇文档中的功能点名称和编号需和需求文档中对应。

    4.1.2 需求获取阶段的工作目标与关键交付物成果¶

    工作目标：

    1. 确定能够准确地了解用户组织、目标及描述需求的人
    2. 定义需求的诱导方法（会议、交谈、文件、记录等）
    3. 挑选参与需求讨论的人、时间、地点
    4. 定义用户构建系统的关键目标和核心需要
    5. 定义用户系统将放置的技术环境（位置、主机和网络、其他环境等）
    6. 确定用户特定应用环境的业务特征，这些特征是系统功能和性能可以或不可以实现的假设和前提条件
    7. 对不明确的、不清晰的、有歧义的需求，最好采用原型方法，或创建一个应用场景进行介绍和说明
    8. 针对用户提出的系统要求，评估业务及技术可行性。如果需要，重复迭代上述过程

    需求获取产生的主要交付物成果：

    1. 参与需求诱导活动的客户、用户和其他干系人的名单
    2. 系统目标与核心关注
    3. 系统技术环境的描述
    4. 系统和产品范围的限定性假设
    5. 功能点列表及相应的假设和限制
    6. 需求和可行性的描述

    4.1.3 需求分析阶段的工作目标与关键交付物成果¶

    需求分析阶段的任务是面向系统实现（最主要的是面向架构设计，还不是代码），严格对系统的需求进行再分析。包括：

    1. 通过仔细地分析系统的输入、输出、功能、属性以及系统的构成环境，决定系统构成的完整集合。
    2. 需求分析主要是面向系统架构及其实现的，
    3. 所讨论的是在技术上,系统应该如何构建并做什么。
    4. 需求分析将引导架构设计（正向作用），也受架构设计方法的制约（反向作用）。

    所以，需求分析阶段是架构师介入项目需求开发的最主要阶段。需求分析的验收标志是组织的需求评审，其内容和性质与需求获取阶段的用户确认，有本质的不同。

    4.1.4 需求处理阶段架构师的关注点¶

    （1）文档

    1. 文档质量会影响到架构师对需求的理解
    2. 需求记录和确定的需求边界、范围等内容，需求的范围边界决定了系统做什么和不做什么

    （2）需求超集

    需求超集通常而言就是业务领域模型。业务领域模型反映了现在以致未来一段时间（产品生命周期内）软件系统的需求。因此，架构师在关注需求的 时候，针对做什么和不做什么，应该有基于更广泛的业务模型的考虑。

    （3）限制与约束

    以构架为中心的软件开发模式，是近几年来软件界大力推崇的一项最佳实践，它较好地解决了软件开发中以往难于克服的多个难题，如需求的变更问题、系统功能扩展的困难、系统的设计基础脆弱的问题等。但由此也给架构师带来了一定的设计局限和约束，例如，开发平台的限制、重用限制、接口限制等。

    （4）基线

    经过评审且不能轻易修改的需求文档

    4.1.5 需求评审阶段架构师的关注点¶

    在需求评审阶段，作为参与评审的一个重要角色是项目经理（假定不是架构师兼任），面对需求评审，负责这个项目团队的项目经理的定位是什么？

    项目经理负责带领项目团队，作为项目的组织和管理者，他要接受评审委员会的审查。因此，他首先是被评审者。但同时，他代表组织（公司）管理项目团队，所以，他也还必须站在公司的立场，他应该站在评审委员会一边。他既不应该一味地为项目团队的缺点进行辩护（辩护与适当的解释和说明不是一回事），也不应简单地指责项目团队的不足。因此，项目经理是处在一个需要充分协调、沟通、中和各方意见和要求的位置。这也是项目经理职业素质、工作经验和知识能力要求比较高的体现。关注评审内容和结果，根据评审委员会的意见，改进需求开发阶段的工作，是项目经理的职责。

    从需求评审以上的活动看，架构师的角色要“简单”一些，他就是项目经理的“技术助手”和具体执行者，他关注构成项目关键点的那些“要素”是什么、在哪里、是否合适等。

    在需求评审阶段，架构师与被评审者——需求分析师的角度显然是不同的。前者是审查者（站在接收者的角度），后者是被审查者（交付者）。但由于架构师也部分参与了需求过程，因此，架构师不可能与需求分析师完全站在对立的“战壕”里。从这个意义上说，需求评审不仅是需求分析师与架构师之间的“交接”，还有很多“第三者”参与和监督。
